A-03Proposed architecture

A modular monolith: one Next.js app on the Node.js runtime and one Postgres database. Modules talk to each other only through their server/ service functions, and the raffle engine depends on nothing above it. The four surfaces (public, admin, presentation, verifier) are thin layers over these modules.

How a repeat-winner rule becomes a constraint

Every rule config compiles to an exclusivity_key that is computed when the winner is inserted:

  • "Win at most once per raffle" → participant_id
  • "At most once per category" → participant_id:category_id
  • "Repeats allowed" → NULL (no constraint)

The candidate filter in code already excludes ineligible people. The unique index is the backstop in case that code has a bug.

Event isolation

Every business table carries event_id, and every query in modules/*/server takes an eventId argument and filters on it. Composite foreign keys ((event_id, id)) make sure, for example, that a prize can only belong to a category in the same event.

Relational data vs validated JSON

Relational

  • Anything that is queried, counted, joined or constrained: participants, prizes, categories, draws, winners, media, imports
  • Built-in participant fields (name, department, job title)
  • Every state machine status

Zod-validated JSONB

  • Participant.custom_values, checked against that event's ParticipantField definitions
  • Prize.eligibility_rule (for example, department filters)
  • EventSettings.presentation (countdown, audio, accent, quality tier)
  • ImportBatch.column_mapping, ImportRow.raw/errors/before_image

Canonical text, not JSONB

  • Snapshots are stored as RFC 8785 canonical JSON text. JSONB reorders keys and rewrites numbers, which would change the bytes and break the SHA-256 hashes.

Deviation from the brief: it suggested separate ParticipantCustomField and ParticipantCustomFieldValue tables (an entity-attribute-value design). I recommend JSONB values checked against field definitions instead. Imports and snapshots are much simpler, and with one admin and thousands of rows there is no query-performance cost. See D3.

Import history and media metadata

  • ImportBatch: kind (participants or prizes), file name, file SHA-256, mapping, status (staged → validated → committed | cancelled | reverted), row and error counts, timestamps.
  • ImportRow: row number, raw values, normalized values, errors, planned action (create, update or skip), target ID, and a before-image so a commit can be reverted before freeze.
  • MediaAsset: event, kind (participant photo, prize photo, event cover, event logo), storage key, MIME type, bytes, width, height, SHA-256, original file name, and the import batch it came from.

Vercel Functions accept request bodies up to about 4.5 MB, so the browser does the heavy work: it reads the files, unzips them and resizes the photos. The server re-validates every row and every image, and nothing reaches the live tables until the admin commits.

7.2 Prepare and freeze

sequenceDiagram
  autonumber
  actor A as Admin
  participant R as raffle server
  participant DB as Postgres
  A->>R: Prepare raffle (event)
  R->>DB: Read eligible participants, prizes, rules
  R->>R: Canonical JSON (RFC 8785), SHA-256 each snapshot
  R->>R: seed = 32 random bytes, commitment = SHA-256(seed)
  R->>R: Encrypt seed (AES-256-GCM, key from env)
  R->>DB: RafflePreparation (draft) + audit
  R-->>A: Manifest preview (hashes, counts, commitment)
  A->>R: Freeze
  R->>DB: Tx: re-hash live data, must equal draft, status frozen, audit
  R-->>A: Pre-draw manifest (JSON + printable)
  Note over A: Shares manifest hash with witnesses before the first draw

After the freeze, the participant, prize and rule services refuse to write anything that affects that event, and they say why. To change anything, the admin has to cancel the preparation with a written reason, which is recorded in the audit chain, and then create a new one (version + 1). The cancelled preparation and its snapshots are kept.

7.3 Draw execution

sequenceDiagram
  autonumber
  actor D as Director console
  participant R as raffle server
  participant DB as Postgres
  participant B as drand quicknet
  D->>R: POST draw (prizeId, idempotencyKey)
  R->>DB: Existing draw for key? return it
  R->>B: Latest round number
  R->>DB: Tx + advisory lock(preparation): verify hashes, next open slot, insert Draw pending with target_round = latest + 2
  Note over R,DB: Target round is committed before it exists
  R->>B: Wait for target round (about 6 s)
  R->>R: Verify BLS signature
  R->>R: Decrypt seed, derive stream, rejection-sample index
  R->>DB: Tx + lock: re-check slot, insert Winner, Draw committed, audit
  R-->>D: Committed draw id (winner withheld from display)
  D->>R: Start reveal
  R->>DB: PresentationCursor phase = revealing

Why the admin can't reroll. The draw row and its target beacon round are committed before that round exists. Retries reuse the same target round, and drand rounds never change once published, so a retry always gives the same winner. A pending draw can't be deleted, only voided through a correction that is recorded in the audit chain and shown on the public verify page.

If drand is unreachable, the draw stays pending_beacon and the console shows "Beacon unavailable – retry". Nothing falls back silently. A CSPRNG-only mode exists, but it has to be chosen in the rule snapshot before freeze, and the manifest then says so.

Selection algorithm pcascade-select-v1

candidates = frozen participants
             filtered by prize.eligibility_rule
             minus exclusivity conflicts with prior committed winners in this preparation
             sorted by participant id (bytewise)
candidate_list_sha256 = SHA-256(canonical(candidates ids))

key   = SHA-256( "PCASCADE/select/v1" ‖ preparation_id ‖ participants_sha256 ‖ rules_sha256
                 ‖ draw_sequence ‖ prize_id ‖ slot_number ‖ server_seed ‖ beacon_round ‖ beacon_randomness )
block_i = HMAC-SHA256(key, uint32be(i))   for i = 0,1,2…
read 8 bytes at a time as uint64 r;  limit = floor(2^64 / n) * n
accept the first r < limit;  index = r mod n        # rejection sampling, no modulo bias
winner = candidates[index]

Every input is stored on the draw or the preparation, or can be derived from them. Once the seed is revealed, anyone with the export bundle can re-run this code, either with tools/verifier or on the /verify page, and check four things separately: snapshot integrity, beacon validity (BLS signature against the published quicknet public key), draw result, and audit-chain integrity.

7.5 Reset operations

Resets change the operational state. They never change the historical record. Both run under the same advisory lock as draws, and both are refused while any draw in the preparation is pending_beacon.

Reset Current Raffle ItemFresh Start
PreconditionThe item's current draw is committed; no draw in flightPreparation is frozen or drawing; no draw in flight
Writes (one transaction)WinnerCorrection(kind=reset_item, reason, previous_draw_id); Winner.voided_at and Draw.status=voided (one-way changes allowed by trigger); slot cursor back to pending; audit entryOld preparation superseded, with reason; its seed is revealed so its draws stay verifiable; new RafflePreparation (new ID, version+1) in draft; audit entry
Next stepA new Draw row for the same slot: new sequence, new idempotency key, new future beacon roundThe admin re-runs prepare and freeze: fresh snapshots, new seed commitment, new manifest
Idempotency keyprevious_draw_id, so resetting the same draw twice returns the first correctionold_preparation_id
KeptOriginal draw, winner, beacon evidence and audit entries, all still verifiableEvery earlier draw, winner, snapshot and audit entry
Public visibilityThe verify page and post-draw report list every reset with its reason and both drawsThe verify page lists superseded sessions; /winners shows only the active session (D12)

Decision (2026-11-20): resets are unlimited. This deliberately overrides the amendment's rule against rerolling until a preferred winner appears. What still applies:

  • A reason is required for every reset: a category from a configured list (winner absent, ineligible, data error, technical issue) plus free text.
  • Every reset is public. The reset count and each voided draw appear on the director console, the verify page and the post-draw report.
  • Whether the voided winner can win the redraw is a setting in the rule snapshot. The default is excluded.

Consequence: the system can't claim that the admin is unable to reroll. The verify page will say plainly that resets are unlimited and that fairness depends on the reset history, which it lists in full.

Animation engine contract

Each scene is a lazy component with the same contract: { winner, prize, accent, quality, onPhase }. It preloads its assets during the countdown, plays a GSAP master timeline, and calls onPhase('revealed') at the end. A scene receives a winner that is already committed and can't change anything. Quality tiers (texture resolution, shadows, particle counts) are chosen by a GPU probe on the presentation machine. Scenes use only original Blender models and CC0 PBR textures and HDRIs.

A-08Security

Authentication and bootstrap

Bootstrap

  • npm run admin:bootstrap runs locally against DATABASE_URL, asks for the password with no echo, and refuses if the admin row exists.
  • There is no HTTP route that creates an admin, ever.
  • Recovery means re-running the CLI with --reset, which needs direct database credentials and is written to the audit chain.

Passwords

  • node:crypto scrypt (N=2^17, r=8, p=1, 16-byte salt), compared with timingSafeEqual. It needs no native dependency and works on every Node runtime.
  • Minimum 12 characters; checked against a bundled common-password list.
  • Changing the password requires the current one and revokes every other session.

Sessions

  • 32-byte random token in a __Host- cookie: HttpOnly, Secure, SameSite=Lax.
  • The database stores only its SHA-256. Sessions expire after 8 hours idle and 7 days at most, and the token rotates on login.
  • requireAdmin() is called in the admin layout and in every server action and route handler. Middleware alone isn't trusted.

Login throttling

  • A LoginAttempt table in Postgres, keyed by hashed IP plus a global counter.
  • Backoff: 5 failures → 1 minute, doubling up to 1 hour. No paid rate-limit service.
  • Every attempt is recorded in the audit chain.

Threat model

A-12Decisions requiring your approval

  1. Hosting. Decided Vercel Hobby; the commercial-use question goes to Vercel in parallel. Original recommendation: Vercel Hobby, only after written confirmation from Vercel that a free, internal, no-revenue company raffle counts as non-commercial. Fallback: production on Cloudflare (needs the CPU-time questions answered). Vercel Pro would break the zero-cost rule.
  2. Photo storage. Decided option C, photos stored in Neon Postgres. Original recommendation: C, Postgres bytea with CDN caching. It needs no extra provider or card, has no upload-operation limits, and imports stay atomic. Use A (R2) if it turns out to need no card and photo volume grows.
  3. Custom fields: JSONB checked against field definitions, instead of separate EAV tables.
  4. Randomness: drand quicknet combined with a committed server seed (pcascade-select-v1). CSPRNG-only mode is allowed only if declared before freeze.
  5. Draw control: a separate director console that needs an admin session, plus a read-only presentation display. They can run on the same laptop in two windows.
  6. Presentation visibility: public once the event is published, or unlisted behind a per-event token.
  7. Data privacy: what may appear publicly (name, department, photo, bio?), whether consent is recorded, and how long data is kept after the event.
  8. Auth: built in-house (scrypt plus database sessions) with no auth library or provider.
  9. ORM: Prisma, with Drizzle as the fallback if the spike shows a blocker.
  10. Correction policy: what happens when a winner is absent or ineligible. Proposal: handle it through Reset Current Raffle Item (§7.5).
